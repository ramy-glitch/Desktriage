# Desktriage Synthetic Dataset Card

## Overview
- **File:** `desktriage_tickets.csv`
- **Format:** CSV (also provided as JSON Lines)
- **Records:** 1,500 synthetic tickets
- **Purpose:** Prototype and test ticket ingestion, category classification, operational priority assessment, confidence-based review, routing, and API integration.
- **Data origin:** Generated synthetically from templates and explicit rules; no real user or patient records are included.

## Schema
1. `ticket_id`: unique synthetic ticket identifier.
2. `user_id`: pseudonymous synthetic user identifier; multiple tickets may share a user.
3. `query_text`: fictional unresolved support query.
4. `escalation_reason`: synthetic reason the upstream assistant escalated the query.
5. `category`: target healthcare-policy domain label.
6. `priority`: target operational priority (`P1`–`P4`).
7. `impact`: simplified impact descriptor used to explain the synthetic priority label.
8. `time_sensitivity`: simplified time-sensitivity descriptor.
9. `requires_human_review`: synthetic expected review flag; not a live model prediction.
10. `assigned_team`: illustrative destination derived from a deterministic category-to-team mapping.
11. `label_source`: provenance of the labels.

## Category taxonomy
- `eligibility_and_enrollment`
- `coverage_and_benefits`
- `claims_and_appeals`
- `costs_and_financial_assistance`
- `access_and_referrals`
- `policy_interpretation`
- `other_or_unknown`

These labels are illustrative and should be aligned with the actual policy domains supported by the upstream assistant before production use.

## Priority policy represented
- **P1:** immediate administrative deadline or material deadline risk.
- **P2:** time-sensitive administrative need requiring prompt review.
- **P3:** routine unresolved query.
- **P4:** non-time-sensitive information request.

Priority is operational handling priority, not clinical urgency or medical severity. These labels are synthetic examples, not clinical advice or validated service-level commitments. The definitions follow the Cabinet Office [Technical incident management guidance](https://digital-handbook.cabinetoffice.gov.uk/docs/software/technical-incident-management-guidance.html).

## Important limitations
- This is a prototype dataset generated from templates and deterministic rules, not a naturally occurring sample of support tickets.
- Query phrasing is repetitive and may contain shortcuts that allow a model to learn template patterns rather than robust intent.
- `category`, `priority`, and `assigned_team` are generated by the data-generation process. They are not independently adjudicated human ground truth.
- `requires_human_review` is a synthetic policy label and is not derived from a calibrated model confidence score.
- The distribution does not represent real-world prevalence.
- Good test scores on this dataset do not demonstrate performance on real Deskline escalations.

## Recommended use
1. Use for API, schema, database, worker, retry, routing, and end-to-end integration tests.
2. For initial ML experiments, split by `user_id` to prevent tickets from the same synthetic user crossing train/test boundaries.
3. Evaluate per-class precision, recall, and F1, plus priority-specific recall and human-review rates.
4. Inspect examples manually and revise labels/taxonomy before treating the dataset as a model benchmark.
5. Seek independently labelled, appropriately authorised real examples for external validity when possible.

## Reproducibility
The dataset was generated with a fixed random seed (42), using rule-based templates and deterministic label assignment. Regenerating it requires the same generation logic and dependencies.
